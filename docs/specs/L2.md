# L2 — Detailed Requirements

These requirements implement the approved [L1 requirements](L1.md). Customer-facing behavior and states trace to the [mock coverage matrix](../mocks/README.md) and [manifest](../mocks/manifest.json). Mock names, dates, prices, addresses, availability, and legal text are sample content; tests use fixture data and configured policies. A displayed amount must identify whether it is a typical range, starting price, estimate, or braider-confirmed amount. All dates and times presented to customers use the appointment's local time zone.

## L2-001: Browse styles
**Traces to:** L1-001

The gallery must show published styles with a name, representative image, and available typical duration and price information, and open the selected style detail.

**Acceptance Criteria:**
1. Given published styles, when a visitor opens the gallery, then each visible card shows its name and image and labels available time and price as typical values.
2. Given a style card, when the visitor opens it, then the detail shown belongs to that style.
3. Given no published styles, when a visitor opens the gallery, then the gallery shows its empty state and no misleading sample cards.

---

## L2-002: Search and categorize styles
**Traces to:** L1-001

Visitors must be able to search published styles by name and select the categories shown in the gallery; the visible cards and active controls must reflect the current criteria.

**Acceptance Criteria:**
1. Given styles in multiple categories, when a visitor selects Braids, Twists, or Locs, then only matching styles appear and the selected category is identified.
2. Given a search term, when the visitor submits or changes the search, then only styles whose searchable name matches the term appear.
3. Given criteria with no matching styles, when results finish loading, then the no-results state offers a way to clear the criteria.
4. Given more styles than one result page holds, when the visitor requests the next page, then the next set appears without duplicating earlier cards and the search and category remain applied.

---

## L2-003: Explain a style
**Traces to:** L1-001

A published style detail must explain its variations, typical duration, typical price, expected wear or upkeep, and factors that can change the final quote, using only fields available for that style.

**Acceptance Criteria:**
1. Given a style with complete editorial data, when its detail opens, then variations, duration, price, wear or upkeep, and quote factors are shown with typical or estimate language.
2. Given a style with an unavailable optional fact, when its detail opens, then that fact is omitted without inventing a value and the remaining detail is usable.
3. Given an unpublished or unknown style identifier, when its detail is requested, then no private draft content is returned and the not-found experience appears.

---

## L2-004: List eligible braiders for a style
**Traces to:** L1-002

Matching results must contain only active, published braiders who offer the selected published style, with service area, applicable starting price or range, rating summary where available, and supplied availability information.

**Acceptance Criteria:**
1. Given braiders who do and do not offer a selected style, when a visitor opens matching results, then only active published braiders with that offered style appear.
2. Given a matching braider with supplied availability, when the result appears, then its displayed availability reflects an offered slot; absent availability is labeled as unavailable or omitted, not invented.
3. Given a braider with no reviews, when the result appears, then it does not display a fabricated rating or review count.
4. Given no eligible braiders, when results load, then the empty state explains that none currently offer the style.

---

## L2-005: Filter matching braiders
**Traces to:** L1-002

Visitors must be able to search and narrow matching braiders by the mock's price and travel-distance criteria without losing the selected style.

**Acceptance Criteria:**
1. Given matching braiders, when a visitor applies a valid maximum price and distance, then every result satisfies the selected style and both filters, and the active filters remain visible.
2. Given an invalid price or distance, when the visitor applies filters, then the dialog identifies the invalid field and preserves the entered values without changing results.
3. Given valid filters with zero results, when filtering completes, then the no-results state offers a clear-filters action that restores results for the selected style.
4. Given a loading or failed filter request, when the dialog is busy or fails, then it prevents duplicate submission and retains the entered criteria for retry.

---

## L2-006: Explain result relevance
**Traces to:** L1-002

Each matching result must identify the selected service that made the braider eligible and link to that braider's profile without claiming a personalized or verified match.

**Acceptance Criteria:**
1. Given a result for knotless braids, when a visitor views it, then it names the braider's knotless-braids service and opens that braider's profile.
2. Given a result with a price or availability summary, when its source service or offered slot changes, then a refreshed result reflects the current published data.

---

## L2-007: Show a braider profile
**Traces to:** L1-003

A public braider profile must show the braider's published identity, services, relevant portfolio, review summary and published reviews, service area, preparation guidance, policies, and a booking route where a request can be made.

**Acceptance Criteria:**
1. Given a published braider with complete information, when a visitor opens the profile, then each available section is shown and the booking action retains that braider's identity.
2. Given missing optional portfolio or reviews, when the profile opens, then the respective section shows an honest empty state while the remaining profile stays usable.
3. Given reviews fail to load but other profile data loads, when the profile opens, then the profile shows its partial-data warning and a retry action for reviews.
4. Given an unpublished or unknown braider, when the profile is requested, then its private details are not exposed.

---

## L2-008: Keep ratings and review evidence accurate
**Traces to:** L1-003

Rating and review counts must derive from published reviews for the braider and must not include removed or pending-moderation reviews.

**Acceptance Criteria:**
1. Given published and unpublished reviews, when a profile or result shows a rating and count, then both use published reviews only.
2. Given no published reviews, when a profile or result appears, then it shows an unrated state rather than a numeric rating.

---

## L2-009: Report a review
**Traces to:** L1-003

An authenticated customer must be able to report a published review with a reason. Reports must enter a moderation workflow without immediately changing the public review.

**Acceptance Criteria:**
1. Given a published review, when a signed-in customer submits a nonblank reason, then a report is recorded for that review and the customer receives confirmation.
2. Given a blank reason, when the customer submits, then the dialog identifies the field and preserves the form.
3. Given a save failure, when the customer retries, then the reason remains available and no successful report is falsely shown.
4. Given a visitor who is not signed in, when they try to submit a report, then they are directed to sign in and no report is created.

---

## L2-010: Create a customer account
**Traces to:** L1-004

Account creation must accept a name, valid email address, and password of at least 12 characters, avoid duplicate accounts for one normalized email, and begin email verification.

**Acceptance Criteria:**
1. Given valid new account details, when the customer submits them, then one account is created and the verification screen explains the next step.
2. Given an invalid email or password shorter than 12 characters, when the customer submits, then field errors appear and no account is created.
3. Given an email already registered, when account creation is attempted, then another account is not created and the response does not reveal sensitive account details.
4. Given a submission in progress or a network failure, when the customer retries, then no duplicate account is created.

---

## L2-011: Sign in and sign out
**Traces to:** L1-004

Customers must be able to sign in with valid credentials and end the authenticated session through the sign-out confirmation dialog.

**Acceptance Criteria:**
1. Given valid credentials, when a customer signs in, then protected customer pages become available to that account.
2. Given invalid credentials, when sign-in fails, then no session is created and the error does not identify which credential was wrong.
3. Given a signed-in customer, when they confirm sign-out, then the session is invalidated and protected customer information is no longer accessible through that session.
4. Given a customer dismisses the sign-out dialog, when they continue browsing, then the existing session remains active.

---

## L2-012: Recover account access
**Traces to:** L1-004

Customers must be able to request a time-limited, single-use password reset link and set a new password of at least 12 characters.

**Acceptance Criteria:**
1. Given a syntactically valid email, when a reset is requested, then the response gives the same neutral confirmation whether or not an account exists.
2. Given a valid unused reset link and matching new passwords of at least 12 characters, when the customer saves them, then the password changes and the link cannot be reused.
3. Given an expired or reused link or mismatched passwords, when a reset is attempted, then the password stays unchanged and an actionable error appears.

---

## L2-013: Verify email
**Traces to:** L1-004

Account email verification must use a time-limited, single-use link and provide a controlled resend action.

**Acceptance Criteria:**
1. Given a valid unused verification link, when the customer opens it, then that account's email is marked verified and a success state appears.
2. Given an expired, altered, or reused link, when it is opened, then no account is changed and the error state offers a valid recovery path.
3. Given a resend request, when it is accepted, then a new link is issued and repeated requests are rate-limited.

---

## L2-014: Maintain account details
**Traces to:** L1-004

An authenticated customer must be able to update their own name, email, and phone number. A changed email must require verification before it is treated as verified contact information.

**Acceptance Criteria:**
1. Given valid changed details, when the customer saves, then their own account reflects the values and the screen confirms success.
2. Given an invalid email, when the customer saves, then the email field identifies the problem and no invalid value is stored.
3. Given a changed email, when it is saved, then the new address remains unverified until its verification link is completed.
4. Given a failed save, when the customer retries, then their edits remain in the form and no success state appears prematurely.

---

## L2-015: Select a bookable service and time
**Traces to:** L1-005

The booking request must use a service currently offered by the selected braider and a currently offered time, and collect customer contact and hair details shown in the mock.

**Acceptance Criteria:**
1. Given a published service and offered slot, when a signed-in customer opens booking, then the service, time, braider, customer contact, and hair-detail fields refer to the selected braider.
2. Given a slot no longer offered or a service no longer published, when the customer submits, then no request is created and the form explains what must be reselected.
3. Given missing required contact or hair details, when the customer submits, then field errors appear and entered values remain available.

---

## L2-016: Review the request before sending
**Traces to:** L1-005

Before final submission, the customer must be able to review the selected service and time, estimated price and duration, location or service area, applicable cancellation policy, contact details, and hair details.

**Acceptance Criteria:**
1. Given a complete booking form, when the customer opens Review request, then the summary shows the current values and explicitly calls price and time unconfirmed.
2. Given a customer closes the review dialog, when they return to the form, then all entered values remain available.
3. Given a material service, slot, estimate, or policy change between form load and submission, when the customer tries to send, then the changed terms are presented for fresh review before a request is created.

---

## L2-017: Submit one pending request
**Traces to:** L1-005

A successful booking submission must create one customer-owned request with a stable reference and an awaiting-reply status; repeat submissions of the same attempt must not create duplicate requests.

**Acceptance Criteria:**
1. Given a reviewed valid request, when the customer sends it, then one request is recorded and the success state links to its detail by reference.
2. Given the customer repeats submission while the first attempt is in progress or retries after a timeout, when the same attempt reaches the server, then it returns the same request rather than creating another.
3. Given the server rejects the request, when the failure is shown, then the customer is told whether a request exists and can retry without guessing.
4. Given a newly submitted request, when its detail loads, then it says Awaiting reply and does not call its time, price, or location confirmed.

---

## L2-018: Show appointment history and status
**Traces to:** L1-006

My Appointments must show only the signed-in customer's requests and appointments, including upcoming and past items and their current status, with links to detail or care and review as appropriate.

**Acceptance Criteria:**
1. Given pending and completed items owned by a customer, when they open My Appointments, then each item shows its service, braider, local date and time, relevant estimate or agreed amount, and status.
2. Given items belonging to another customer, when the first customer opens their list, then those items do not appear.
3. Given no appointments, when the list loads, then the empty state directs the customer to explore styles.
4. Given a search or filter with no matches, when it is applied, then the no-results state offers a way to clear it.

---

## L2-019: Show request and appointment detail
**Traces to:** L1-006

The detail screen must reflect the current lifecycle state and show the service, braider, local time, price status, available location, contact path, policy, preparation checklist, and allowed actions.

**Acceptance Criteria:**
1. Given a pending request, when its owner opens detail, then the status is Awaiting reply, price is labeled an estimate, and a private studio address is withheld.
2. Given an accepted request, when its owner opens detail, then the status is Confirmed and the accepted time, agreed amount or confirmed estimate, and authorized location are shown.
3. Given an incomplete optional section, when detail loads, then a partial-data warning identifies what is unavailable while the core appointment facts remain visible.
4. Given an unknown or other-customer reference, when detail is requested, then no appointment data is exposed.

---

## L2-020: Accept or decline a request
**Traces to:** L1-006

The request's braider must be able to accept or decline it from an existing authenticated management surface. Acceptance must record the agreed time and amount status; a stale response must not overwrite a later state.

**Acceptance Criteria:**
1. Given a pending request assigned to a braider, when that braider accepts with the time and agreed amount status, then the request becomes confirmed and its owner sees those details.
2. Given a pending request, when the assigned braider declines it, then the owner sees a declined status and the slot is no longer presented as confirmed.
3. Given a request already accepted, declined, or cancelled, when an old accept or decline action arrives, then its current status remains unchanged and the braider is told to refresh.
4. Given a different braider, when they attempt to respond, then the action is denied without exposing private request details.

---

## L2-021: Request an appointment change
**Traces to:** L1-006

An owner must be able to propose a new offered time where the appointment policy permits changes; the existing agreed time remains authoritative until the assigned braider accepts the change.

**Acceptance Criteria:**
1. Given a changeable request or appointment, when its owner submits a valid offered replacement time, then a change request is recorded and both current and proposed times are clearly distinguished.
2. Given an invalid or unavailable proposed time, when the owner submits, then no change is recorded and the dialog retains the entered value with an error.
3. Given the assigned braider accepts or declines the proposed change, when the owner revisits detail, then the displayed time and status reflect the decision.
4. Given the policy disallows changes or the appointment is terminal, when a change is attempted, then it is rejected without altering the agreed time.

---

## L2-022: Cancel a request or appointment
**Traces to:** L1-006

An owner must be able to review the applicable cancellation terms and explicitly confirm cancellation where the current policy permits it.

**Acceptance Criteria:**
1. Given a cancellable item, when its owner opens the cancellation dialog, then the applicable terms and item reference are shown before confirmation.
2. Given the owner dismisses the dialog, when they return to detail, then the item status is unchanged.
3. Given the owner confirms cancellation, when it succeeds, then the item is cancelled once and both customer and braider views reflect that state.
4. Given cancellation is disallowed or save fails, when the owner attempts it, then the item remains in its prior state and an actionable error appears.

---

## L2-023: Repeat a completed service
**Traces to:** L1-006

Rebooking must preselect the completed appointment's braider and service when still offered and require the customer to choose a current offered time and review current terms.

**Acceptance Criteria:**
1. Given a completed appointment whose service is still offered, when its owner selects book again, then a new booking form opens with that braider and service preselected and no old time assumed available.
2. Given the service is no longer offered, when the owner selects book again, then no new request is created and the customer is guided to current services.

---

## L2-024: Show care and preparation guidance
**Traces to:** L1-007

The platform must show the braider's relevant preparation checklist before a visit and the booked style's care guidance after a completed visit when content is available.

**Acceptance Criteria:**
1. Given an appointment with preparation guidance, when its owner opens detail, then the checklist for that service is shown.
2. Given a completed appointment with care guidance, when its owner opens Care and Review, then the guidance for the booked style is shown with its source.
3. Given missing guidance, when the page opens, then no invented instruction appears and the remaining appointment or review actions stay usable.

---

## L2-025: Review a completed visit
**Traces to:** L1-007

An owner must be able to submit one rating from 1 through 5 and a written review for a completed appointment; the review must remain associated with its braider and appointment.

**Acceptance Criteria:**
1. Given a completed unreviewed appointment, when its owner submits a valid rating and nonblank review, then one review is recorded and a success state appears.
2. Given a rating outside 1 through 5 or blank review, when the owner submits, then field errors appear and no review is created.
3. Given a pending, cancelled, or other-customer appointment, when review submission is attempted, then it is denied.
4. Given a review already submitted for that appointment, when the owner repeats the submission, then a second review is not created.
5. Given a transient submission failure, when the customer retries, then their rating and text remain available.

---

## L2-026: Maintain published services
**Traces to:** L1-008

An authenticated braider must be able to add, revise, unpublish, and remove their own style-linked offerings, including a starting price or range, typical duration, and service-specific preparation details.

**Acceptance Criteria:**
1. Given valid service details, when the owning braider publishes them, then that service can appear in style matching and booking with its current values.
2. Given an invalid negative price, nonpositive duration, or missing style, when publication is attempted, then no invalid service becomes public.
3. Given a service is unpublished, when visitors browse matches or booking choices, then it is no longer offered for new requests while historical appointments retain their recorded details.
4. Given another braider's service, when a braider attempts to edit it, then the action is denied.

---

## L2-027: Maintain portfolio, area, and policies
**Traces to:** L1-008

A braider must be able to maintain their own publishable portfolio material, service area, booking and cancellation terms, and preparation guidance; private contact or studio details must follow the visibility rules of the customer journey.

**Acceptance Criteria:**
1. Given valid updates by a braider, when published, then the public profile and matching result reflect the new portfolio and service area.
2. Given a changed policy, when a new customer reviews a request, then the current policy is shown; existing requests preserve the terms accepted at submission.
3. Given a private studio address, when a visitor or pending-request customer views the braider, then the address is withheld until the authorized appointment state permits disclosure.
4. Given uploaded portfolio content of a disallowed type or size, when submitted, then it is rejected without publishing it.

---

## L2-028: Maintain offered availability
**Traces to:** L1-008

A braider must be able to publish, revise, and withdraw their own offered slots; booking must validate slot availability at submission and response time.

**Acceptance Criteria:**
1. Given a future offered slot, when its braider publishes it, then customers can see and select it for that braider's relevant service.
2. Given a withdrawn, past, or conflicting slot, when a customer tries to request it, then no request is created for that unavailable slot.
3. Given two concurrent requests or responses competing for one slot, when one is accepted, then the other cannot also become confirmed for that slot.
4. Given another braider's slot, when a braider attempts to change it, then the action is denied.

---

## L2-029: Create and display notification updates
**Traces to:** L1-009

Customer notification records must be created for material booking, review, account, and privacy events and link to the relevant owned destination when one exists.

**Acceptance Criteria:**
1. Given a request accepted, declined, changed, or cancelled, when the event is recorded, then its customer receives a notification describing the actual state and a working appointment link.
2. Given a review or account action succeeds or fails, when feedback appears, then its wording matches the persisted result and does not claim an unsaved change.
3. Given an unrelated customer's notification, when a customer opens their notification center, then it is absent.
4. Given an unavailable destination, when a notification is opened, then it leads to a safe error or unavailable state rather than another user's data.

---

## L2-030: Read and manage notifications
**Traces to:** L1-009

The notification center must show owned notifications in recent-first order with read and unread states, permit marking an item read, and show an empty state when none exist.

**Acceptance Criteria:**
1. Given read and unread notifications, when their owner opens the center, then each state is identified and the newest notification appears first.
2. Given an unread notification, when its owner opens or marks it read, then its unread count decreases once and the item remains available as read.
3. Given no notifications, when the center loads, then its empty state appears.
4. Given an offline or failed load, when the center cannot refresh, then it identifies the stale or unavailable state without inventing new updates.

---

## L2-031: Show timely on-screen feedback
**Traces to:** L1-009

Booking, review, account, and cookie actions must use the mock's informational, success, warning, and danger feedback patterns, including action, stacked, and persistent variants where appropriate.

**Acceptance Criteria:**
1. Given a successful action, when its feedback appears, then the message identifies the completed action and may dismiss after the documented interval unless focused.
2. Given a failed action, when its feedback appears, then the error remains available until dismissed or resolved and offers a retry where possible.
3. Given multiple simultaneous messages, when they appear, then each remains readable and its action targets the event that produced it.
4. Given a notification with an Undo or View update action, when the action is activated, then it performs that specific operation or opens its relevant destination.

---

## L2-032: Provide help and support path
**Traces to:** L1-010

The help page must explain requests, estimates, changes, and reviews and provide an actionable support contact path that can include a request reference.

**Acceptance Criteria:**
1. Given a visitor opens Help, when content loads, then each of the four topics and a support contact action are available.
2. Given an authenticated customer opens Help from an appointment, when they contact support, then the appointment reference can be included without exposing another customer's information.
3. Given Help fails to load or the customer is offline, when the page appears, then an error or offline state provides a safe retry or contact path.

---

## L2-033: Publish terms and privacy information
**Traces to:** L1-010

Public Terms and Privacy pages must show approved, current product text and remain reachable from the customer shell and relevant account or booking flows.

**Acceptance Criteria:**
1. Given published legal content, when a visitor opens Terms or Privacy, then the current approved text and its effective date are shown without requiring sign-in.
2. Given a booking or account flow, when the customer follows a Terms or Privacy link, then the corresponding public page opens.
3. Given legal content cannot load, when a visitor opens the page, then an error state appears rather than illustrative mock copy presented as policy.

---

## L2-034: Manage optional cookie preferences
**Traces to:** L1-010

Visitors must be able to accept or decline optional usage storage independently of essential storage, revise the choice later, and receive accurate save feedback.

**Acceptance Criteria:**
1. Given no saved optional preference, when a visitor first reaches the site, then the consent notice offers a choice without enabling optional storage beforehand.
2. Given a visitor saves acceptance or rejection, when they return, then the saved preference is applied and can be revised in Cookie preferences.
3. Given a preference save failure, when the dialog reports failure, then it preserves the selected value and does not claim the preference was saved.
4. Given the visitor declines optional storage, when they continue using discovery and account essentials, then those core functions remain available.

---

## L2-035: Present loading, empty, and no-results states
**Traces to:** L1-011

Each page must implement the applicable states listed for it in the mock manifest and distinguish an empty data set from criteria that yield no results.

**Acceptance Criteria:**
1. Given a page request is pending, when a customer opens that page, then its loading state identifies the page or region being loaded.
2. Given successful loading with no owned or published items, when an applicable page finishes, then its empty state appears with a relevant next action.
3. Given valid filters that match nothing, when results finish, then the no-results state retains the criteria and offers a way to clear them.
4. Given a long result set, when it loads, then pagination or continuation is available and no content becomes unreachable.

---

## L2-036: Preserve work through failures
**Traces to:** L1-011

Validation, submitting, failed, partial, and offline states must match the manifest and preserve entered work when retry is possible.

**Acceptance Criteria:**
1. Given invalid form data, when submission is attempted, then a summary and field-specific errors identify the issue and keep valid entries.
2. Given a submission in progress, when the customer activates Submit again, then no second operation begins and a busy state is announced.
3. Given a transient failure, when the customer retries, then entered form data remains and any previous server result is reconciled before a new state-changing attempt.
4. Given optional data fails while core data succeeds, when the page renders, then its partial state identifies the missing region and offers a targeted retry.
5. Given connectivity is lost, when the customer visits a supported page, then the offline state explains what remains available and that new requests need a connection.

---

## L2-037: Route to safe error destinations
**Traces to:** L1-011

Unknown pages, unauthorized resources, server errors, and offline navigation must use the corresponding mock destination with an appropriate next action.

**Acceptance Criteria:**
1. Given an unknown route, when it is opened, then the not-found page offers a way back to style discovery.
2. Given a protected route without a valid session, when it is opened, then the customer is directed to sign in without revealing protected data.
3. Given a forbidden resource, when an authenticated customer requests it, then the access-unavailable page appears without revealing whether another customer's appointment exists.
4. Given a server error after a state-changing action, when the error page appears, then it does not silently resubmit that action.

---

## L2-038: Authenticate and authorize requests
**Traces to:** L1-012

Customer-owned and braider-owned API resources and actions must require authentication and enforce ownership or assigned-braider authorization; published discovery, Help, Terms, and Privacy remain intentionally public.

**Acceptance Criteria:**
1. Given no authenticated session, when a protected API action is requested, then it is denied and no private data is returned.
2. Given customer A, when they request or mutate customer B's appointment, review draft, notification, or account record, then the action is denied without disclosing the record.
3. Given braider A, when they request or mutate braider B's offering, slot, or assigned request, then the action is denied.
4. Given an anonymous visitor, when they request a published style, published braider, Help, Terms, or Privacy, then the public content remains accessible.

---

## L2-039: Validate and protect untrusted content
**Traces to:** L1-012

The API must validate submitted fields and media; rendered user content must not execute code; private contact, reset, verification, and appointment data must be protected in storage and transit.

**Acceptance Criteria:**
1. Given malformed, oversized, or unexpected input for a booking, account, review, report, or braider update, when it reaches the API, then it is rejected without persisting invalid data.
2. Given script-like text in a review, hair detail, or profile field, when the content is rendered, then it appears as text and cannot execute in the browser.
3. Given a reset or verification token, when it is stored or logged, then the reusable secret is not exposed in readable application logs.
4. Given customer contact or confirmed studio information, when an anonymous or unrelated user requests a public resource, then those private fields are absent.

---

## L2-040: Resist abuse of public and account actions
**Traces to:** L1-012

Account, password recovery, verification resend, review reporting, and booking submission must have server-side abuse controls that preserve a usable recovery path.

**Acceptance Criteria:**
1. Given repeated sign-in failures or reset or verification requests above the configured limit, when another request is made, then it is rate-limited with a retry indication and no account detail is disclosed.
2. Given repeated review reports or booking submissions above the configured limit, when another action is attempted, then it is controlled without creating duplicate records.
3. Given a legitimate customer after the limit's configured recovery interval, when they retry a valid action, then the action is available again.

---

## L2-041: Provide keyboard and screen-reader access
**Traces to:** L1-013

Customer pages, dialogs, forms, notifications, and navigation must meet WCAG 2.2 AA behavior and retain the mock's accessible labels and state semantics.

**Acceptance Criteria:**
1. Given keyboard-only use, when a customer moves through every customer screen, then all actions are reachable, focus is visible, and focus order follows the content order.
2. Given an open dialog, when it opens, then focus moves inside; when it closes by Escape or a close action, then focus returns to its trigger.
3. Given a form error or state change, when it appears, then a screen reader receives the summary or status and each invalid field is programmatically associated with its message.
4. Given a light or dark theme, when text, controls, and focus indicators appear, then they meet WCAG 2.2 AA applicable contrast and target-size criteria.

---

## L2-042: Adapt layout and theme
**Traces to:** L1-013

Every customer-facing mock screen and dialog must remain usable at extra-small (<576 px), small (576–767 px), medium (768–991 px), large (992–1199 px), and extra-large (≥1200 px) widths, and in light and dark themes.

**Acceptance Criteria:**
1. Given each of the five viewport ranges, when a customer opens a page, dialog, or notification, then primary content and actions are visible without horizontal page scrolling or clipped controls.
2. Given an extra-small viewport, when a customer opens a multi-column page, then content follows a readable single-column order and dialogs fit the viewport with their actions reachable.
3. Given a theme switch, when the customer toggles light or dark, then all page, dialog, and notification surfaces use the selected theme and the choice persists across navigation.
4. Given text zoom to 200% or browser zoom to 400%, when a customer uses a page or dialog, then content and actions remain readable and operable.

---

## L2-043: Meet customer journey performance targets
**Traces to:** L1-014

Core discovery and owned-data reads must have measurable latency targets under the project's agreed reference load, without omitting loading and failure feedback.

**Acceptance Criteria:**
1. Given the agreed reference load of 50 concurrent users and warm application instances, when published gallery, style detail, matching results, or braider profile API reads are measured, then at least 95% complete within 500 ms, excluding client network time.
2. Given the same load, when customer appointment list or detail API reads are measured, then at least 95% complete within 750 ms, excluding client network time.
3. Given a read exceeds its normal loading interval, when the UI is waiting, then the corresponding mock loading state remains available and the page does not appear falsely complete.

## L2-044: Make mutations reliable and observable
**Traces to:** L1-014

State-changing actions must produce an unambiguous durable outcome, tolerate safe retries, and emit diagnosable request and failure records without private content or secrets.

**Acceptance Criteria:**
1. Given a booking, cancellation, change, acceptance, review, or account update, when it succeeds, then a subsequent read returns the durable state and a retry cannot create an unintended duplicate transition.
2. Given a handled validation, authorization, conflict, or service failure, when the API responds, then the recorded outcome includes its actual response status, correlation identifier, operation, and duration.
3. Given an operational error, when logs are inspected, then passwords, reset or verification secrets, hair details, private contact data, and full request bodies are absent.
4. Given temporary service unavailability, when the dependency recovers and the customer retries, then the current durable state is retrieved before another irreversible action is attempted.

## L2-045: Protect offline appointment data
**Traces to:** L1-014

Previously available appointment summaries may remain readable offline for the current customer, while new requests and mutations must wait for a connection; locally held customer data must be removed at sign-out.

**Acceptance Criteria:**
1. Given a signed-in customer has previously opened an appointment, when connectivity is lost, then the offline experience can show its last saved summary labeled with its last-updated time and does not claim it is current.
2. Given the customer is offline, when they attempt a new booking or mutation, then no success is claimed and the action waits for an explicit online retry.
3. Given the customer signs out, when another person opens the same browser session, then the prior customer's locally held appointment data is unavailable.

## L2-046: Restrict the management app to braiders
**Traces to:** L1-015

The braider management app must require an authenticated braider session; customer accounts and visitors must not reach braider requests, offerings, profile content, or availability through it.

**Acceptance Criteria:**
1. Given valid braider credentials, when a braider signs in to the management app, then their booking requests screen opens for their own account.
2. Given valid customer credentials, when they are used to sign in to the management app, then no management session is created and the screen explains that the app is for braider accounts without revealing other account details.
3. Given no session, when any management route is opened, then the braider is directed to the management sign-in screen and no braider data is requested or shown.
4. Given a signed-in braider, when they confirm sign-out, then the management session ends and management routes again require sign-in.

## L2-047: Present braider management states
**Traces to:** L1-015

Each braider management screen and dialog must implement the states listed for it in the mock manifest, edit through dialogs or dedicated screens rather than inline page forms, and report conflicts without overwriting newer data.

**Acceptance Criteria:**
1. Given a management screen request is pending, when the braider opens it, then its loading state identifies the region being loaded.
2. Given a braider with no requests, services, portfolio items, or offered slots, when the corresponding screen loads, then its empty state explains the next action.
3. Given a failed or offline load, when the screen appears, then an error or offline state offers a retry and invents no data.
4. Given an edit whose underlying record changed since it was loaded, when the braider saves, then the screen reports the conflict, keeps the braider's input, and offers to refresh.
5. Given a successful change, when the save completes, then the list reflects the saved values and on-screen feedback names the completed action.

## L2-048: Provide a theme control
**Traces to:** L1-013

The customer and braider app shells must offer a visible light and dark theme control whose current state is exposed to assistive technology. Without a saved choice, the theme must follow the system preference.

**Acceptance Criteria:**
1. Given no saved theme choice, when a visitor opens any page, then the page uses the system's light or dark preference.
2. Given the theme control, when a visitor activates it, then the theme switches, the control's pressed state and label reflect the active theme, and every visible surface uses the selected theme.
3. Given a saved theme choice, when the visitor navigates or reloads, then the saved theme is applied before content is shown, without a flash of the other theme.
