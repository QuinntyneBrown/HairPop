Inline message

Inline messages sit right next to what they describe: a hint under a field, the error that says how to fix it, a quiet Saved beside a form.

WCAG 2.2 AALinked with aria-describedbyStatus: stable

Overview

Use an inline message for feedback that belongs to one control or one small area, placed where the eye already is. Use an alert for a condition that affects a region or the page (and the error summary that lists every invalid field), and a toast for feedback about an action that has finished elsewhere.

  • Field hint (.field__help): what to enter, shown before anyone makes a mistake: "Use at least 12 characters."
  • Field error (.field__error): what is wrong and how to fix it, shown after validation.
  • Counter (.field__counter): characters used against a limit, under a review textarea.
  • Inline status (.inline-status): a short state beside a form or row: "Saving…", "Saved just now", "Not saved".

Anatomy

  1. Warning glyph (errors)Generated "⚠" with empty alternative text, so it is not read aloud; pairs the colour with a shape.
  2. MessageBody small, --color-danger-fg for errors and --color-fg-muted for hints; 4px under the control.
  3. Link to the controlThe message's id is in the control's aria-describedby; errors also set aria-invalid="true".

Sizes

Inline messages use the body-small size everywhere so they stay subordinate to the control they describe.

Messages are not interactive; their state follows the control and the data. The control's own hover and focus states are shown for context.

  • Timing: validate on blur, then re-validate on every input so the error disappears as soon as the value is fixed.
  • Hint plus error: keep the hint; put the error first in aria-describedby so it is read first.
  • Over limit: data-over="true" turns the counter danger and the textarea invalid; never truncate what was typed.

Responsive behaviour

  • Messages wrap under their control at any width; they never sit beside it, so they cannot overflow at 360px.
  • In two-column form rows (768px and up), each field keeps its own message; rows align to the top so a long error does not push its neighbour.
  • Inline status wraps below the form's actions on phones.

Theming

Hints read --color-fg-muted, errors and over-limit counters --color-danger-fg, counters --color-fg-subtle, and status tones their --color-*-fg. In dark mode the danger text lightens to red-300 so it stays above 4.5:1 on grey-900.

/* Hints inside a dialog keep the dialog's muted colour */
.dialog .field__help { color: var(--color-fg-muted); }

Accessibility

Role and pattern

Plain text tied to its control with aria-describedby; errors add aria-invalid="true" to the control. Inline status that changes after load sits in a role="status" element so "Saved just now" is announced politely. The message lives outside the <label>, so it is not part of the field's name.

Keyboard

KeyAction
TabFocus goes to the control; its hint or error is read as its description. Messages are never focusable.

Focus

On a failed submit, focus moves to the error summary, whose links move focus into each invalid field; the inline error is then read with the field.

Labelling

Errors name the problem and the fix in the field's terms ("Enter a 10-digit phone number"). The "⚠" glyph has empty alternative text (content: "⚠" / ""). Counters say "of 500 characters", not just "23/500".

Motion

Messages appear without animation. The live dot pulses over --duration-loop-pulse and pauses under reduced motion (--motion-loop-state).

Touch

Not a target. Keep errors directly under the field so they are visible above the on-screen keyboard.

Content

  • Errors are one sentence: what to do, with an example when the format is unclear: "Enter an email address like name@example.com."
  • Never blame ("You entered an invalid value") and never be vague ("Enter a valid value to continue").
  • Hints explain constraints before they bite: "Use at least 12 characters."
  • Status is two or three words, past tense for done: "Saved just now", "Not saved".
