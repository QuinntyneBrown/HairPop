Progress bar

A progress bar shows how far a task with a known length has come, or that a longer task is still moving when its length is unknown.

WCAG 2.2 AArole="progressbar"Status: stableCore set

Overview

Use a progress bar when a task takes longer than about a second and you can say how far along it is: uploading inspiration photos for Nia, saving a long review with photos, importing past appointments. Use the indeterminate bar only when the task is long and its length is truly unknown.

  • For content that is loading into a known layout, use a skeleton instead.
  • For a short wait tied to one control ("Send request"), use the button's loading state or an inline spinner.
  • No mock uses a progress bar yet; it is part of the core set so the first upload flow has a ready, accessible pattern.

Anatomy

  1. LabelSays what is happening, in the present tense; it names the progress bar.
  2. Value (optional)An <output> with a count or percentage, tabular numbers.
  3. Action (optional)One small button at the end of the label row: "Cancel upload" while running, "Retry upload" after a failure.
  4. Track8px tall, full radius, --color-bg-subtle-hover.
  5. FillWidth from --value; --progress-fill (accent, success or danger).

Variants

Choose determinate whenever you can count something (bytes, files, steps). The ending colour tells the outcome, and the label always says it too.

Bar only

Inside a dense row (a photo thumbnail, a list item) the bar can stand alone, but it still needs an accessible name through aria-label.

A bare bar named with aria-label.
HTML
<div class="progress" role="progressbar" aria-label="Uploading braids-front.jpg" aria-valuemin="0" aria-valuemax="100" aria-valuenow="40"><div class="progress__bar" style="--value: 40%;"></div></div>

Sizes

One size: an 8px track. Emphasis comes from the label, not a thicker bar.

States

A progress bar is not interactive, so it has no hover, focus, active or disabled states. Its states are where the task is.

Determinate
Indeterminate

An indeterminate task that finishes switches to a full success or danger bar so the ending is visible; the label changes in the same update ("Appointments imported", "Import stopped").

Both themes

Responsive behaviour

  • The bar is always 100% of its container; it never sets its own width. Place it in a .progress-field inside the form or dialog it reports on.
  • The label, value and action share one row; when they do not fit, the label keeps the first line and the value and action wrap onto the next, never truncating or squeezing the count. Keep the label short so it rarely wraps.
  • In a bottom-sheet dialog on phones, the progress field sits above the sticky footer so it is never covered.

Theming

The fill reads one component token, --progress-fill, which .progress--success and .progress--danger point at --color-success-solid and --color-danger-solid. The track is --color-bg-subtle-hover. In the dark theme the accent lightens to plum 300 and the track to grey 700, so the fill stays clearly brighter than the track.

Inside a toast the fill reads --color-fg-inverse (.toast .progress in components.css), so it stays quiet on the inverse surface.

Accessibility

Role and pattern

role="progressbar" on .progress (see WAI-ARIA progressbar). Determinate bars set aria-valuemin, aria-valuemax and aria-valuenow, plus aria-valuetext when a count reads better than a percentage ("2 of 3 photos"). Indeterminate bars omit aria-valuenow. The region it reports on sets aria-busy="true" until the task ends.

Keyboard

KeyAction
TabNot focusable; focus stays on the control that started the task (or a Cancel button beside the bar).

Focus

The bar never takes focus. If the task can be stopped, put a "Cancel upload" button next to the label; it receives focus with the shared ring.

Labelling

Name the bar with aria-labelledby pointing at the visible label, or aria-label when there is none. Do not announce every percentage: screen readers read the value on demand. Announce the start and the outcome once through a polite live region or toast ("Photos uploaded", "Upload stopped: connection lost").

Contrast

Accent fill on surface
Success fill on surface
Danger fill on surface
Label on surface
Value on surface

The track itself is decorative; the fill, label and value carry the information.

Forced colours

The track gets a CanvasText hairline outline and the fill opts out of adjustment with a Highlight background, so the reached value stays visible.

Motion

Determinate fills animate width over --duration-deliberate (500ms); reduced motion makes the change instant. The indeterminate sweep loops on --duration-loop-shimmer and pauses under prefers-reduced-motion through --motion-loop-state, leaving a still 40% segment; the label still says the task is running.

Touch

Not a target. The Cancel or Retry action is a small button (32px tall), above the 24px minimum target.

Content

  • Label the task in the present tense while it runs ("Uploading inspiration photos") and the outcome when it ends ("Photos uploaded", "Upload stopped: connection lost").
  • Prefer counts people understand ("2 of 3 photos") over raw percentages; never show both.
  • On failure, say what is kept and what to do: "Your other photos are saved. Retry when connected."
  • Do not promise a time remaining unless it is accurate.

Sources

No mock shows a progress bar; it is part of the core set and its CSS comes from the mocks' kit (docs/mocks/assets/ui.css). The closest mocks, where a submit is pending, show why a button state is preferred for short tasks:

  • pages/booking-request/submitting (short submit; button loading state instead of a bar)
  • dialogs/cookie-preferences/busy (busy dialog footer)

Drift fixed during extraction: the indeterminate loop used a raw 1.4s duration (now --duration-loop-shimmer) and was stopped by a global !important reduced-motion override (now paused through --motion-loop-state); the fill transition used --duration-slow (now --duration-deliberate, the token reserved for progress).
